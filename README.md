# Vice-clean-NVIDIA

A compatibility layer that runs Grand Theft Auto VI's Xbox Series build
natively on Windows, from files **you** supply, tuned for **NVIDIA RTX**
cards. The title's x86-64 code runs unchanged inside our process; the layer
supplies the console's platform underneath it (loader, runtime services,
Direct3D 12.X on the PC's Direct3D 12) and recompiles its GPU shaders to
DXIL on first use. See [docs/architecture.md](docs/architecture.md).

It is [VIctory-NVIDIA](https://github.com/trustno1-coder/VIctory-NVIDIA)
(its game, DLSS and frame generation work) with clean, checked code on top:
every path the title reaches returns an error instead of panicking, the
contract for changes is written down and checked
([AGENTS.md](AGENTS.md)), and the numbers below come from commands, not from
numbers typed by hand.

> **This repository contains no game files, code or assets.** You need your
> own legally obtained copy of the title. It is not affiliated with or endorsed
> by the title's developer or publisher, nor by NVIDIA. See
> [docs/asset-policy.md](docs/asset-policy.md).

## Reporting a problem

Please attach **both** logs from the run that went wrong. Without them we can
only guess. Paste `%LOCALAPPDATA%` into the address bar of File Explorer to
get there.

1. **The play log**, in `%LOCALAPPDATA%\victory\logs\`: the newest
   `victory-nvidia-play-<date>-<time>-<number>.jsonl` (from `victory.exe`) or
   `victory-nvidia-<date>-<time>.log` (from the script launcher). The window
   shows its path at the start, on the line `Log: ...`.
2. **The crash log**: `%LOCALAPPDATA%\VIctory\data\7952987A\crashes.log`, and,
   if there is one from that run, the newest `victory-<date>-<time>-<number>.crash.log`
   in `%LOCALAPPDATA%\VIctory\data\7952987A\temp\`.

Also say which GPU, Windows version (10 or 11) and release you used.

## Where it stands

Tested on one PC: Windows 11, Ryzen 7 9800X3D, 64 GB RAM, **GeForce RTX 5070
12 GB**; the title's Xbox Series build v1.0.2.1, Series X profile, 2560x1440
output, DLSS Quality. Frame rates are the layer's own count, in the opening
rooms.

| | |
|---|---|
| Opening rooms | mostly 26-30 frames a second rendered (33-38 ms a frame) |
| Frame generation | 2x to 6x on top of that: by Streamline's own count, exactly 2, 4 and 6 frames shown for each one rendered |
| Device losses, crashes | none in the measured runs |
| Before the foxhound base (Series S, 720p to 1080p by DLSS) | 15-17 frames a second in the same rooms |

foxhound's own measurements, on an RTX 4070 SUPER, are in
[its README](docs/README-foxhound.md).

What is known to be wrong:

- **No ray tracing.** The title's own is off (`VICTORY_BVH_BUILDER=1`, or the
  menu's RAY TRACING, turns it on: slow and with a broken picture on this
  base). An estimate stands in for indirect light and reflections.
- **Frame generation needs room in the card's memory.** The layer fills the
  card with textures up to its budget; with frame generation on from the start
  the launcher holds a fifth of the budget back (a little less while it is only
  ready), so a few more textures can come late. Switched on from the menu on a
  full 12 GB card it can still say that memory is past the budget; it then
  runs, perhaps unevenly.
- **Frames are only generated while the game's window has the focus**, and
  about a second passes after a change before they come.
- **The first run of every new build stutters** while the driver compiles
  pipelines (`victory preload`, or the F1 menu's PRELOAD SHADERS, makes them
  ahead).
- "SAVE AND RESTART NOW" can leave the old game's process behind without a
  window; it goes when the PC restarts.
- What foxhound lists as wrong (the heat-haze pass left out, hitches in
  cutscenes) applies here too.

## Quick start

You need Windows 10 or 11, 32 GB of RAM or more, an SSD, an NVIDIA GeForce
RTX card with a recent driver, and **your own dump** of the title's Xbox
Series build v1.0.2.1 (the folder with `game_scarlett_master.exe`).

**Without building anything:** download `victory.exe` from
[VIctory-NVIDIA's latest release](https://github.com/trustno1-coder/VIctory-NVIDIA/releases/latest)
(the upstream this repository follows; its releases do not hold this
repository's changes), put it next to `game_scarlett_master.exe` and
double-click it. Windows may say the publisher is unknown (the file is not
signed): "More info", then "Run anyway".

**Building it yourself:** install [Rust](https://rustup.rs) (the toolchain is
pinned) and the
[Visual Studio Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/)
with "Desktop development with C++", then in PowerShell:

```powershell
git clone https://github.com/victordecarli/Vice-clean-NVIDIA
cd Vice-clean-NVIDIA
cargo build --release -p victory
copy target\release\victory.exe D:\Games\MyDump\    # beside your game_scarlett_master.exe
```

`victory.exe` started with no command (a double click) is `victory play`.
The [script launcher](#the-script-launcher) builds and starts it in one
step instead.

What the first start does:

- It asks once whether to download NVIDIA's DLSS and frame generation files
  (about 70 MB) from NVIDIA's own GitHub. They are NVIDIA's and are not part
  of this program; say no and the game still runs, with its own upscaling and
  no frame generation.
- On Windows 10 it offers to fetch Microsoft's newer Direct3D 12 runtime (the
  D3D12 Agility SDK, `D3D12Core.dll`, about 22 MB from nuget.org) into a
  `D3D12` folder beside `victory.exe`: Windows 10's own stops at shader model
  6.5, and the translated shaders need 6.6 (without it the game shows a black
  screen and closes within seconds). The file is checked against Microsoft's
  signature and the tested SHA-256. Windows 11 keeps using its own runtime.
- **The first start of each new version restarts by itself once.** A new
  `victory.exe` runs at about 14 fps on its first start, and normally from then
  on. So the first start plays about 20 seconds, says so at the top of the
  picture, and starts the game again. It doesn't happen again for that version
  (a mark is kept in `%LOCALAPPDATA%\victory\warmed`).

Settings, saves, caches, logs and NVIDIA's and AMD's files are kept under
`%LOCALAPPDATA%\victory`; the one exception is the Windows 10 runtime above.

**In the game:**

- **F1** brings up the settings menu (arrow keys pick and change, Enter does
  it): DLSS, frame generation, frame rate cap, console profile, picture size,
  the light estimates and the main speed switches, saved to
  `victory-settings.txt` and applied at the next start ("SAVE AND RESTART NOW"
  does that for you; lines marked LIVE change at once).
- **F3** shows the stats panel: frame rate and frame time, frames shown with
  frame generation, draws, how busy the GPU and the submitting thread are,
  copies, RAM and VRAM.

## Frame generation: what your card supports

| Your card | Frame generation | Limits |
| --- | --- | --- |
| GeForce RTX 40 and RTX 50 | **DLSS frame generation** | 2x on RTX 40; more than 2x (up to 6x) needs an RTX 50 |
| GeForce RTX 20 and RTX 30 | **AMD FSR 3 frame generation** (DLSS frame generation needs an RTX 40 or later) | **2x at most**. DLSS upscaling still works on these cards, so the Series X profile is fine |
| Other cards (no DLSS) | **AMD FSR 3 frame generation** | **2x at most, Series S profile only** (F1 menu, CONSOLE): without DLSS the game's own upscaler, which FSR 3 needs, only takes the Series S sizes. Not tested here |

- **At every start the game tells you** which one your card runs, and why
  not if it can't, at the top of the picture for the first 30 seconds (and
  in the console window).
- **F1 menu, FRAME GEN TYPE**: AUTO (DLSS where the card has it, else FSR 3),
  DLSS, or FSR 3 (also on an RTX 40/50, if you prefer it). FRAME GENERATION
  switches it off or on.
- FSR 3 needs AMD's FidelityFX DLLs (`amd_fidelityfx_loader_dx12.dll` and
  `amd_fidelityfx_framegeneration_dx12.dll`, about 30 MB). They are AMD's and
  not part of this program. On a card without DLSS frame generation (or with
  FSR 3 chosen in F1) the first start of `victory.exe` asks once whether to
  download them from AMD's own GitHub (the FidelityFX SDK);
  `victory.exe get-fsr` does it later, and `Get-AMD-FSR.cmd` does it for the
  script launcher. Each file is checked against the copy this fork was tested
  with, and only loaded with AMD's valid signature. A `fidelityfx` folder next
  to `victory.exe`, or `VICTORY_FIDELITYFX_DIR`, works too.
- RTX 20 and 30 cards can try DLSS frame generation with the
  [MFG Unlocker](https://github.com/dashdogy/MFG-Unlocker) mod (not ours, and
  not tested here, which was only run on an RTX 50). It is an option, off by
  default: **F1, MFG UNLOCKER, ON**, then restart. On, the next start
  downloads it by itself from the mod's own GitHub release (v1.7.2, about 5 MB,
  checked against the SHA-256 its author published) into
  `%LOCALAPPDATA%\victory\mfg-unlocker`, and every start loads it. Nothing is
  renamed or copied. On an RTX 20 or 30 the first start also asks once (No unless
  you type y). `victory.exe get-mfg` downloads it by hand. The mod writes its own
  `RTXMFG-...` logs and settings beside `victory.exe`, and Backspace opens its
  menu. The start's notice says "UNLOCKED BY A MOD" and the log says it was
  loaded. If the game crashes or frame generation fails, turn it off in F1 (or
  add `VICTORY_MFG_UNLOCKER=` to `%LOCALAPPDATA%\victory\victory-settings.txt`).
  FSR 3 frame generation (2x) is the supported way on those cards. A
  `winmm.dll` copy of the mod beside `victory.exe` still works too.

## Playing

`victory play [exe]` starts the title with this fork's settings. Without a
path it takes `game_scarlett_master.exe` beside the program, else in the
current folder. Its options (`victory play --help`):

| Option | What |
|---|---|
| *(none)* | Series X profile, 2560x1440, DLSS Quality, no frame rate cap, frame generation ready but off |
| `--framegen 4` | DLSS frame generation on from the start, 2 to 6 frames shown for each one rendered |
| `--fg-type auto` / `dlss` / `fsr` | which frame generation (see above) |
| `--no-framegen-ready` | frame generation not made ready at the start (the menu cannot switch it on) |
| `--dlss off` / `dlaa` / `balanced` / `performance` | the title's own upscaling, or another DLSS mode |
| `--fps 60` | a frame rate cap (30 is the title's own) |
| `--series-s` | the Series S profile: 1280x720 inside, faster, softer |
| `--res 1080to1440` / `4k` | scene at 1080p upscaled by the title / the stock 3840x2160 output |
| `--preload` | make every shader and pipeline before the title starts (`victory preload`): a while, maybe long |
| `--set VICTORY_X=1` | add or override any switch, as often as needed |

What the F1 menu saved (`victory-settings.txt`) goes over these at every
start; delete that file to go back to them. Full screen: start the game, then
run `.\scripts\fullscreen.ps1` in another window.

### The script launcher

```powershell
copy victory.example.toml victory.toml      # then set game_dir to your dump's folder, outside this one
.\Get-NVIDIA-DLSS.cmd                        # once: NVIDIA's DLSS and frame generation files, about 70 MB
scripts\play-nvidia.ps1 -Exe 'D:\Games\MyDump\game_scarlett_master.exe'
```

The first start builds the layer (a few minutes). `Get-NVIDIA-DLSS.cmd` gets
NVIDIA's files from
[NVIDIA-RTX/Streamline](https://github.com/NVIDIA-RTX/Streamline) into
`nvidia-sdk\` (git-ignored). They are NVIDIA's, under NVIDIA's licences, which
are saved beside them; this repository does not carry them and may not. Nothing
is downloaded unless you run that file; `VICTORY_STREAMLINE_DIR` names another
folder if you have the Streamline SDK already.

`scripts\play-nvidia.ps1` is `scripts\play-foxhound.ps1` under the name
VIctory-NVIDIA has always had; its options:

| Option | What |
|---|---|
| *(none)* | Series X profile, 2560x1440, DLSS Quality, no frame rate cap, frame generation ready but off |
| `-FrameGen`, `-FrameGenX 4` | frame generation on from the start, 2 to 6 frames shown for each one rendered |
| `-Dlss off` / `dlaa` / `balanced` / `performance` | the title's own upscaling, or another DLSS mode |
| `-Fps 60` | a frame rate cap (30 is the title's own) |
| `-SeriesS` | the Series S profile: 1280x720 inside, faster, softer |
| `-Res 1080to1440` / `4k` | scene at 1080p upscaled by the title / the stock 3840x2160 output |
| `-NoFrameGenReady` | frame generation only with `-FrameGen` (it is otherwise made ready at every start, so the menu can switch it) |
| `-FgType auto` / `dlss` / `fsr` | which frame generation; FSR 3's DLLs from `VICTORY_FIDELITYFX_DIR`, else `amd-sdk\FidelityFX\bin` here |
| `-Build diag` | the diagnostics build (slower; captures, timelines, recording time in the F3 panel) |
| `-More @{VICTORY_X='1'}` | add or override any switch |

## Commands

`victory help <command>` describes each in full.

| Command | What |
|---|---|
| `play [exe]` | the title with this fork's settings (see [Playing](#playing)) |
| `run <exe> [--execute]` | prepare, map and bind the title's executable; with `--execute`, run it. `--console series-x\|series-s`, `--strict` (no host pass-through), `--unimplemented trap\|zero`, title arguments after `--` |
| `preload [paths]` | `shaders`, then `warm`, over the title's folder |
| `shaders [paths]` | translate every shader into the shader cache, so that no run has to |
| `warm` | make the host pipelines of every pipeline the title ever created, for the driver's cache |
| `get-dlss`, `get-fsr`, `get-d3d12`, `get-mfg` | fetch NVIDIA's, AMD's, Microsoft's or the MFG Unlocker's files (see above) |
| `upscaler-check` | check Streamline, DLSS and frame generation on this PC without the title |
| `config` | show the resolved configuration and check it |
| `translate [paths]` | run every shader through the translator and report what it cannot handle yet: `--validate`, `--pipelines`, `--list`, `--jobs N`, `--json <file>` |
| `inspect <exe\|dll>`, `census [paths]`, `lib-exports <lib>`, `shader-info [paths]` | look at images, their imports and the shader containers |

`translate --json <file>` writes the counts per kind of program (found, and
validated: emitted as DXIL the validator accepts), aggregate numbers only,
and whether every file was read; a file it cannot read is named on stderr.
`cargo xtask progress --record <file>` turns that into the
[Shader translation](#shader-translation) block. `translate` also reads
`VICTORY_HOST_WAVE=32` (translate for a GPU of 32-lane waves),
`VICTORY_DXIL=<path>` (the `dxil.dll` `--validate` loads; default: the newest
Windows SDK's) and `VICTORY_EMIT_DUMP=<dir>` (with `--validate`, the first
shaders failing each validator error; with `--list`, every emitted shader;
outside the repository).

## Debugging

Logs: `victory play` writes one per start under `%LOCALAPPDATA%\victory\logs`
(the ten newest are kept); any command writes its lines to a file too with
`VICTORY_LOG_FILE=<path>`. The file has one JSON object per line, each
event's fields beside its `timestamp` (UTC), `level`, `target` and thread; a
crash is the last line (`"message":"crash"`), and a `victory play` log starts
with `run_start` (the console model, build, switches and mods). For example:
`jq -c 'select(.level == "WARN")' victory-nvidia-play-*.jsonl`. Events with
the target `victory::summary` are logged whatever the filter;
`VICTORY_LOG=victory_loader=trace,info` filters the rest. A release build logs info and above; debug and trace lines, and most
switches below, need the diagnostics build:

```powershell
cargo build --profile diag -p victory --features diagnostics   # target\diag\victory.exe
```

| Variable | Effect |
|----------|--------|
| `VICTORY_D3D12_DEBUG=1` | the host debug layer: names the command of an invalid call |
| `VICTORY_D3D12_GBV=1` | with the above, GPU-based validation (slow) |
| `VICTORY_D3D12_DRED=1` | on a GPU failure (hang, page fault), the allocation hit and the commands in flight |
| `VICTORY_D3D12_WARP=1` | diagnostics build: the software adapter, where a shader's wild access is a crash report instead of a driver reset |
| `VICTORY_STACKS=20,60` | diagnostics build: every thread's stack at those seconds |
| `VICTORY_WATCH=<rva>,...` | diagnostics build: logs a title u32 whenever it changes |
| `VICTORY_KEYS=30:Enter,35:X` | presses keys at those seconds |
| `VICTORY_CRASH_SAVE=<rva>:<len>,...` | diagnostics build: saves those title ranges (hex) to the cache folder on a crash |
| `VICTORY_CAPTURE=<dir>` | saves presented frames there |
| `VICTORY_RECORD=<dir>` | diagnostics build: records a frame's GPU work to run again ([docs/replay.md](docs/replay.md)) |
| `VICTORY_SKIP_PIPELINES=<hash>,...` | diagnostics build: leaves out the draws and dispatches whose pipeline holds a listed shader hash |
| `VICTORY_GPU_TIMING=1` | diagnostics build: each list of a submission run and timed on its own |
| `VICTORY_SHADER_LOOP_LIMIT=<n>` | diagnostics build: translated shader loops stop after `n` iterations per lane |
| `VICTORY_AUDIO_CAPTURE=<file.wav>` | diagnostics build: records what the title plays |

foxhound's README lists more switches (*Switches worth knowing*). Crashes and
host GPU failures go to `crashes.log` in the title's data folder in every
build.

## Developing

[AGENTS.md](AGENTS.md) is the contract for every change, by people and by
coding agents alike: the project map, the hard rules (no panics on paths the
title reaches, no swallowed errors, `unsafe` with its reason), the commands to
run before calling a change done, and the pitfalls this code has had. Each
crate with gotchas of its own has an `AGENTS.md` beside its code.

```powershell
cargo xtask install-hooks       # the asset-policy check on every commit
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked # needs no game data
```

- `cargo xtask citations` fails when a path the contract cites is gone.
- `cargo xtask wincheck` type-checks and lints the Windows code from any host;
  the `portable` CI job runs it on Linux, beside the crates that build there.
- `cargo xtask progress` writes the [Shader translation](#shader-translation)
  block; a test fails when it and the measurement disagree.
- `cargo xtask audit-metrics` counts and grades every crate (it gates nothing).

## Where it comes from

Over several weeks the same NVIDIA PC built, ran and measured many projects for
this title: Leonida,
[Marvisak's VIctory](https://github.com/Marvisak/VIctory),
[fxceless's fork](https://github.com/fxceless/victory-fork),
[the 7900 XTX fork](https://github.com/avatarmanz/VIctory-7900XTX),
[Belobug's](https://github.com/Belobug/VIctory-Belobug-AMD),
[DexNom's](https://github.com/DexNom/VIctory),
[CGBJ's cool_fox](https://github.com/codec-d/cool_fox), Kelvaroq's, Neptune,
xcl (another layer for the same title) and then
[foxhound](https://github.com/readmet3xt-lab/foxhound). On each, what stopped it
on an RTX card was found, fixed or worked around, and measured, and what was
learned went on to the next. That work is
[VIctory-NVIDIA](https://github.com/trustno1-coder/VIctory-NVIDIA), which this
repository follows.

On 2026-11-26 VIctory-NVIDIA moved onto
[readmet3xt-lab/foxhound](https://github.com/readmet3xt-lab/foxhound)
(`02fc18a`, GPL-3.0-or-later): on the same PC it ran the same rooms at close
to twice the frame rate, at a higher resolution. foxhound brings the Series X
profile at a native 2560x1440, DLSS Super Resolution and Frame Generation
through NVIDIA Streamline (loaded when the game runs; nothing of NVIDIA's is
needed to build), and an estimate of indirect light and reflections in place
of the title's ray tracing. Its own README is kept as
[docs/README-foxhound.md](docs/README-foxhound.md); its measurements are in
[docs/findings.md](docs/findings.md).

What VIctory-NVIDIA adds on top of foxhound, in this tree:

- **The F1 settings menu and the F3 stats panel**, in every build.
- **DLSS frame generation from 2x to 6x**, switched and changed while playing,
  without a restart, and the card's memory shared out so that it has room on a
  full 12 GB card.
- **The title's own 30 frames a second lifted**, with the frame rate at the top
  left of the picture (`FPS: 28.4  FG: 170.4`).
- **Open water without dark blocks**: two of the title's water light programs
  run on 32-lane cards only in a form that left whole tiles of the sea dark and
  cost about 15 ms of the card a frame; they are left out there (WATER LIGHT in
  the menu, `VICTORY_WATER_LIGHT=1`, runs them again).
- **One command to play**, and **`Get-NVIDIA-DLSS.cmd`**: the eight NVIDIA
  files that are loaded, about 70 MB, taken out of NVIDIA's 263 MB release.
- The foxhound line also carries VIctory-NVIDIA's earlier work in its own form:
  the descriptor slot pool that stopped NVIDIA's view heap cap from dropping
  draws, memory compares on the card, the Series S interface plane and the face
  network. The black-blob scrub, the graphics card picker and the ray-tracing
  builder path are in the history, and come over as this base needs them.

What this repository adds on top of VIctory-NVIDIA:

- **No panics on paths the title reaches**: no `unwrap` or `expect` outside
  tests, and the shader emitter's internal invariants return an error the
  pipeline creation reports instead of aborting the title.
- **A contract and checks for every change**: [AGENTS.md](AGENTS.md), the
  workspace lints with `-D warnings`, rustfmt over the whole tree, and CI on
  Windows and Linux.
- **The shader share measured, not typed**: `translate --json` and
  `cargo xtask progress` above.
